Salt: por que a mesma senha não deveria gerar sempre o mesmo hash

Digite uma senha e clique no botão várias vezes: cada clique sorteia um "sal" (número aleatório) diferente e recalcula o hash colando o sal antes da senha. Repare que o hash muda a cada clique — mesmo sendo sempre a mesma senha.

Digite uma senha acima…
É por isso que dois usuários com a senha "123456" em um banco de dados com salt têm hashes completamente diferentes armazenados — e é por isso que um ataque com tabela pré-calculada (rainbow table) não funciona contra hashes salteados: o atacante teria que refazer a tabela inteira para cada salt.

📚 Resumo

O que os 5 laboratórios mostraram

Hash é mão única

Fácil calcular o hash a partir da senha; matematicamente inviável fazer o caminho inverso (do hash de volta para a senha). É por isso que sites armazenam o hash, não a senha em texto puro.

Efeito avalanche

Uma diferença mínima na entrada (1 letra maiúscula) produz uma saída completamente diferente e imprevisível — não dá para "chutar" a senha original olhando padrões no hash.

Salt evita hash repetido

Sem salt, duas contas com a mesma senha têm o mesmo hash salvo — um vazamento expõe todo mundo que usa aquela senha de uma vez. Com salt, cada conta tem um hash único mesmo com senha igual.

Senha fraca cai sem "quebrar" nada

Um ataque de dicionário não reverte o hash: só compara com hashes de senhas já conhecidas. Comprimento + variedade de caracteres é o que encarece um ataque de força bruta de verdade.
